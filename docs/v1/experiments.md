## D2 — 다운스케일 파이프라인 + YOLO11n/s baseline

### 실행 환경 (2026-07-31 구축)

WSL Ubuntu-24.04 의 시스템 파이썬(3.12.3)에는 `pip` 도 `ensurepip` 도 없고
`apt install python3.12-venv` 를 할 sudo 권한도 없었다. `uv`(0.12.0) 를
`~/.local/bin` 에 사용자 권한으로 설치해 우회했다.

| 항목 | 값 |
|---|---|
| venv | `~/venvs/sod` (WSL 네이티브 디스크) |
| torch | 2.6.0+cu124, CUDA 사용 가능 |
| ultralytics | 8.4.113 |
| GPU | RTX 4070 12GB |

**venv 와 변환된 데이터셋을 저장소(`/mnt/d/sod-project`) 밖에 둔 이유.**
`/mnt/d` 는 Windows 드라이브 마운트라 파일 I/O 가 느린데, 학습은 epoch 마다
이미지를 전부 다시 읽는다. 변환 산출물은 `~/.cache/sod-datasets` (네이티브
디스크)에 쓰고, 원본 `data/` 만 저장소에 남긴다. 경로는 전부
`SOD_DATA_ROOT` / `SOD_BUILD_ROOT` / `SOD_RUNS_ROOT` 로 덮어쓸 수 있다
(`sod/config.py`).

### D1 수치와의 대조 — "중앙값 231px" 은 정의가 달랐다

D1 은 MVTec Screws 객체 한 변 중앙값을 231px 로 기록했다. D2 파이프라인이
같은 라벨에서 뽑은 값은 211.5px 이라 언뜻 안 맞아 보이는데, **정의가 다른 것**
이지 어느 쪽이 틀린 게 아니다:

| 정의 | 중앙값(px) |
|---|---|
| 회전 박스의 긴 변 `max(width, height)` | 231.9 |
| 회전 박스 면적 기준 `sqrt(width*height)` | 171.6 |
| 외접 축정렬 박스 면적 기준 `sqrt(area)` (D2 가 쓰는 값) | 211.5 |

앞으로 "객체 크기"는 전부 세 번째 정의(외접 축정렬 박스의 `sqrt(area)`)로
통일한다 — COCO small 기준(면적 32x32px)과 같은 축이라 비교가 되기 때문이다.

### 결정 1 — 다운스케일은 이미지를 복제하지 않고 `imgsz` 로 준다

원래 계획은 "원본을 단계적으로 축소해 저장"이었는데, YOLO 학습·추론은 어차피
모든 이미지를 `imgsz` 정사각 캔버스로 레터박스 리사이즈한다. 따라서
"이미지를 1/2 로 줄여 저장 후 imgsz=1024 학습" 과 "원본을 imgsz=512 로 학습"은
네트워크가 보는 텐서 기준으로 같은 실험이다. 후자를 택한 이유:

- 리샘플링이 두 번이 아니라 한 번이라 축소 방식이 하나로 통제된다.
- 스케일 단계마다 데이터셋 사본을 디스크에 복제하지 않는다(원본만 2.1GB).

**기준 해상도는 YOLO 표준 640 이 아니라 1024 로 잡았다.** 640 기준이면 1/8
스케일이 80px 인데 80 은 stride 32 의 배수가 아니라 실제로는 64(=1/10)로
밀린다. 1024 는 네 스케일이 1024/512/256/128 로 정확히 떨어져 곡선의 x축이
명목 배율과 일치하고, 원본 1920x1440(MVTec)에도 더 가깝다.

### 결정 2 — NPU-BOLT 자연 small 14장을 통째로 held-out 대조군으로

project-plan.md 2.2절이 요구하는 대조군은 "자연 발생 small 121개(14장) 전체"다.
그 14장을 일반 70/15/15 분할에 섞으면 대부분 train 으로 가고 val/test 에는
십수 개만 남아 지표가 무의미해진다. 그래서 small 인스턴스를 하나라도 가진
14장을 `small_control` 분할로 통째로 빼내고, train/val/test 는 나머지 323장을
70/15/15(seed 0)로 나눴다.

**대가 — 반드시 결과와 같이 읽을 것.** 학습셋에 자연 발생 small 예시가 0개가
된다. 따라서 small_control 성능이 낮아도 그게 "다운스케일 방법론의 한계"
때문인지 "그런 예시를 한 번도 안 봐서" 때문인지 이 실험만으로는 분리되지
않는다. 이 실험이 답하는 건 **"다운스케일로 학습한 모델이 진짜 작게 찍힌
객체로 전이되는가"** 다.

### 결정 3 — MVTec 회전 박스는 외접 축정렬 박스로 변환

YOLO11 은 축정렬 박스만 다룬다. 회전 박스 `(row, col, w, h, phi)` 를 중심은
유지한 채 외접 AABB 로 바꾼다(`sod/data/mvtec.py: rotated_to_aabb`). 라벨이
실제보다 커지는 손실이 있다 — 회전 박스를 그대로 쓰는(OBB) 실험은 D3 이후
별도 축으로 남긴다.

라벨 형식 확인 사항: `bbox` 앞 두 값은 COCO 의 `(x, y)` 가 아니라 `(row, col)`
= `(y, x)` 이고 좌상단이 아니라 **중심**이다. `width`/`height` 는 반길이가
아니라 전체 길이다(`area == width * height` 로 확인). `phi` 는 라디안(-pi..pi).

| 데이터셋 | train | val | test | small_control |
|---|---|---|---|---|
| mvtec-screws | 269장 / 3,119건 | 55장 / 647건 | 60장 / 661건 | - |
| npu-bolt | 226장 / 750건 | 48장 / 158건 | 49장 / 154건 | **14장 / 213건** (그중 small 121건) |

MVTec 분할은 데이터셋이 제공하는 `mvtec_screws_{train,val,test}.json` 을 그대로

PCBsmd 는 `smd`(supercategory=none) 자리표시자 카테고리를 빼고 4종만 쓴다 —
안 빼면 인스턴스 0개인 클래스가 하나 끼어 들어간다.

### 스케일별 실제 객체 픽셀 크기 (곡선의 x축)

레터박스 리사이즈 후 `sqrt(area)` 중앙값. 같은 배율이라도 데이터셋 원본
해상도가 달라 객체 픽셀 크기가 전혀 다르다 — 그래서 곡선은 명목 배율이 아니라
이 값을 x축으로 그린다.

| 스케일 | imgsz | mvtec val | npu-bolt val | npu-bolt small_control |
|---|---|---|---|---|
| 1 | 1024 | 112.9px (small 0.5%) | 67.3px (7.0%) | 46.5px (15.0%) |
| 1/2 | 512 | 56.5px (26.6%) | 33.6px (48.7%) | 23.3px (77.9%) |
| 1/4 | 256 | 28.2px (64.1%) | 16.8px (80.4%) | 11.6px (96.7%) |
| 1/8 | 128 | 14.1px (89.5%) | 8.4px (96.2%) | 5.8px (100%) |

괄호 안은 COCO small(32x32px 미만) 비율. **원본 해상도에서는 셋 다 small 이
0%였는데(D1), 학습 해상도로 리사이즈하는 것만으로 이미 상당 비율이 small 이
된다** — scale 1.0 에서도 mvtec 0.5% / npu-bolt 7.0% / 대조군 15.0%. D1 이
"이 데이터셋들은 소형 객체 벤치마크가 아니다"라고 한 건 원본 해상도 기준이고,
탐지기가 실제로 보는 텐서 기준으로는 이미 소형 문제가 섞여 있다.

### 학습 설정

YOLO11n / YOLO11s, 100 epochs, patience 30, AutoBatch, seed 0, deterministic.
**평가 imgsz 는 학습 imgsz 와 같게 맞춘다** — 이 실험의 변수는 "네트워크가 보는
객체 픽셀 크기" 하나이므로, 학습만 작게 하고 평가를 크게 하면 축이 섞인다.
런당 2~12분, 16회 합계 약 1시간 40분 (RTX 4070).

PCBsmd 만 **50 epochs / patience 15** 로 돌렸다 — train 이 6,129장으로 MVTec
(269장)의 23배라 같은 프로토콜이면 12~16시간이 걸린다. epoch 당 가중치 갱신
횟수가 23배라 50 epochs 로도 수렴에는 충분하지만, **다른 두 데이터셋과 학습
조건이 동일하지 않다**는 점은 데이터셋 간 절대 수치를 비교할 때 반드시 감안할 것.

### 읽어낸 것 1 — "몇 px 부터 무너지는가"에 데이터셋 무관한 답은 없다

세 데이터셋을 같은 x축(네트워크 입력에서의 객체 중앙값 px)에 놓으면 붕괴
지점이 전혀 다르다:

| 객체 중앙값 | ~67px | ~34px | ~17px | ~8px |
|---|---|---|---|---|
| pcbsmd (yolo11n mAP50) | 0.995 | 0.995 | 0.994 | **0.919** |
| npu-bolt (yolo11n mAP50) | 0.547 | 0.445 | 0.340 | 0.168 |

같은 8.4px 에서 PCBsmd 는 0.919 를 유지하고 NPU-BOLT 는 0.168 이다. MVTec 은
그 중간으로, 28.2px 까지 0.944(n)/0.987(s) 를 유지하다 14.1px 에서 0.331/0.472
로 급락한다.

즉 붕괴 지점을 정하는 건 픽셀 크기 **단독**이 아니라 픽셀 크기 x (배경 복잡도 ·
대비 · 클래스당 인스턴스 수)다. PCBsmd 는 균일한 PCB 배경에 클래스 4종·23,061
건이라 8px 에서도 버티고, NPU-BOLT 는 자연 배경에 희소 클래스(31건·54건)를
포함해 67px 에서도 이미 낮다. **"소형 객체 탐지의 한계는 N px"** 같은 단일
숫자로 이 프로젝트를 결론내면 안 된다 — 데이터셋별 곡선으로만 말할 수 있다.

부수적으로, COCO 가 small 로 정의하는 32px 경계는 세 데이터셋 어디에서도
변곡점이 아니다. **"작다"의 실질적 기준선은 COCO 정의와 무관하다** — D1 이
"이 데이터셋들은 small 비율이 0%라 소형 벤치마크가 아니다"라고 판단할 때 쓴
기준 자체가 탐지 난이도와는 다른 축이었음을 뒷받침한다.

### 읽어낸 것 1-보강 — mAP@0.5 만 보면 열화를 통째로 놓친다

PCBsmd 의 mAP@0.5 는 8.4px 까지 0.99->0.92 로 거의 평평해서 "이 데이터셋은
작아져도 멀쩡하다"로 읽힌다. 그런데 **같은 런의 mAP@0.5:0.95 는 0.816 -> 0.522
로 36% 떨어진다.** 작아질 때 먼저 무너지는 건 "찾았는가"가 아니라 **"얼마나
정확히 감쌌는가"** 이기 때문이다 — 객체가 8px 이면 1px 오차가 IoU 를 크게
흔든다.

세 데이터셋 모두 mAP@0.5:0.95 쪽 하락폭이 더 크다(MVTec n: 0.918->0.242,
NPU-BOLT n: 0.388->0.085). 따라서 **이 프로젝트의 기본 지표는 mAP@0.5 가 아니라
mAP@0.5:0.95 로 둔다.** D4(SAHI)·D5(copy-paste)가 개선을 주장할 때도 mAP@0.5
만 보고하면 개선 여지가 이미 포화된 구간에서 "효과 없음"으로 잘못 결론날 수 있다.

### 읽어낸 것 2 — 모델 용량은 소형 구간에서만 값을 한다 (세 데이터셋 전부 재현)

n 과 s 의 차이는 큰 객체 구간에서 0.000~0.002 로 사실상 없다가, 각 데이터셋이
꺾이기 시작하는 지점에서만 벌어진다:

| 데이터셋 | 큰 객체 구간 s-n | 꺾이는 지점 s-n |
|---|---|---|
| mvtec-screws | +0.002 (112.9px) | +0.043 (28.2px), +0.141 (14.1px) |
| pcbsmd (mAP50) | +0.000 (67.3px) | +0.037 (8.4px) |
| pcbsmd (mAP50-95) | +0.008 (67.3px) | +0.121 (8.4px) |

"모델을 키우면 좋아진다"가 아니라 **"작은 객체에서만 좋아진다"** 가 정확한
서술이다. D3(YOLO26 STAL)이 개선을 주장한다면 비교해야 할 곳도 이 구간이다.
(NPU-BOLT 는 희소 클래스 잡음 때문에 이 비교에서 제외 — 아래 절 참고.)

### 읽어낸 것 3 — 다운스케일 곡선은 진짜 소형 객체 성능을 과대평가하고, 작아질수록 더 과대평가한다

이 프로젝트의 핵심 질문(2.2절)에 대한 첫 실측 답. 절대 격차가 아니라 **비율**로
봐야 한다 — 둘 다 0 으로 수렴하면 절대 격차는 오히려 다시 줄어들기 때문이다.

| val 객체 중앙값 | 67.3px | 33.6px | 16.8px | 8.4px |
|---|---|---|---|---|
| small_control / val (yolo11n) | 93% | 89% | **71%** | **61%** |
| small_control / val (yolo11s) | 91% | 79% | 61% | 0% |

큰 객체 구간에서는 대조군이 val 의 90% 이상을 따라오다가, 작아질수록 단조롭게
벌어진다. **다운스케일로 만든 곡선을 "이 모델이 작은 물체에 얼마나 강한가"의
답으로 그대로 쓰면 안 된다**는 계획서의 우려가 수치로 확인됐다. 낙관적 상한으로
취급하라는 2.2절의 지침이 옳았다.

주의 세 가지:
- 대조군은 14장·213건(그중 small 121건)뿐이다. yolo11s 의 89%->79% 처럼 한
  단계가 튀는 건 표본 잡음일 수 있어 **곡선의 방향만 읽고 개별 값은 읽지 않는다.**
- 학습셋에 자연 발생 small 이 0개다(결정 2). 이 격차에는 "다운스케일이 실제
  소형을 못 흉내낸다"와 "그런 예시를 한 번도 안 봤다"가 섞여 있다.
- yolo11s 의 8.4px(0.012)는 학습이 사실상 실패한 경우다. 같은 조건 yolo11n 이
  0.168 을 내는데 s 가 0.012 로 무너진 건 크기 효과가 아니라 **imgsz=128 에서
  더 큰 모델이 학습에 실패한 것**으로 보인다(patience 30 조기 종료, 학습 106초).
  이 점은 D3 로 넘어가기 전 재현 확인이 필요한 미해결 항목이다.

### 해결됨 — NPU-BOLT 의 낮은 절대 수치는 희소 클래스 2종이 만든 것이다

우리 baseline 최고치는 val mAP50 0.570(yolo11s, imgsz 1024)인데 NPU-BOLT 논문은
YOLOv5-l 기준 AP 97.38%/91.88% 를 보고한다. 클래스별 AP 를 봤더니
(`scripts/04_per_class_ap.py`, `outputs/d2_per_class_ap_npu-bolt.json`) 원인이
분명했다 — **모델이 못 하는 게 아니라 mAP 가 클래스 평균이라서다.**

yolo11s, imgsz 1024, val 기준:

| 클래스 | train 인스턴스 | val AP50 |
|---|---|---|
| bolt nut | 462 | **0.927** |
| bolt head | 203 | **0.841** |
| blur bolt | 54 | 0.405 |
| bolt side | **31** | 0.106 |
| (4종 평균 = mAP50) | | 0.570 |

인스턴스가 충분한 두 클래스는 0.84~0.93 으로 공개 보고치와 같은 수준이고,
학습 인스턴스가 31개·54개뿐인 두 클래스가 평균을 절반으로 끌어내린다.
따라서 앞선 "미해결" 후보 중 (2) 클래스 불균형이 지배적 원인이고, (1) 분할
차이는 그 불균형을 우리 분할이 더 악화시킨 형태로 기여한다. (3) 모델 크기는
n->s 차이가 0.023 에 불과해 지배적이지 않다.

**부수적으로 드러난 분할 결함: test 분할은 희소 클래스 평가에 못 쓴다.**
323장을 무작위 70/15/15 로 나눈 결과 test 에 `blur bolt` 2건 / `bolt side` 3건만
남았다. 이 클래스들의 test AP(0.007/0.043 등)는 지표가 아니라 잡음이다.
`npubolt.py` 는 small_control 만 계층화하고 클래스는 안 봤다.

> **D3 착수 시 선행 과제 (2026-07-31 결정).** NPU-BOLT 를 클래스 계층화
> 분할로 다시 나누고 8회를 재학습한다(약 40분). D2 에서 지금 하지 않는 이유:
> 곡선의 결론은 양쪽 표본이 충분한 `bolt nut` 기준으로 이미 검증됐고(아래 절),
> 재분할하면 D2 의 16회 중 8회를 다시 돌려야 한다. D3 는 YOLO26 과 baseline 을
> 나란히 비교하는 단계라 희소 클래스 잡음이 남아 있으면 비교가 흐려지므로,
> **재분할 -> baseline 8회 재학습 -> YOLO26 학습** 순서로 D3 를 시작한다.
> D2 의 NPU-BOLT 수치는 이 재분할 이전 것이라 D3 수치와 직접 비교하지 않는다.

|---|---|---|---|---|
| train | 54 | 203 | 462 | 31 |

### 읽어낸 것 3 한계 — 대조군과 val 은 리샘플링 방향이 반대다 (2026-08-03 추가)

NPU-BOLT 는 이미지 크기가 262x230~4896x3672 로 제각각이라, 같은 imgsz 로
맞춰도 **사진마다 리샘플링 방향이 다르다.** 대조군은 원본이 작은 사진(340x230,
425x394 …)이 많아 대부분 **확대**되고, 일반 val 은 대부분 **크게 축소**된다.

| imgsz | val 확대 비율 | val 중앙 배율 | 대조군 확대 비율 | 대조군 중앙 배율 |
|---|---|---|---|---|
| 1024 | 21% | 0.28x | **86%** | **1.44x** |
| 512 | 4% | 0.14x | 21% | 0.72x |
| 256 | 0% | 0.07x | 0% | 0.36x |
| 128 | 0% | 0.04x | 0% | 0.18x |

즉 imgsz 1024 에서는 **일반 사진은 3.6배 축소돼 안티앨리어싱으로 깨끗해지고,
대조군 14장 중 12장은 보간으로 최대 3배까지 늘어나 흐려진다.** "축소한 사진 vs
진짜 작게 찍힌 사진"을 비교한다고 했지만, 그 구간에서는 실제로 "많이 축소된 것
vs 확대된 것"을 비교한 셈이다.

**다만 이것이 82% -> 50% 하락의 원인은 아니다.** 원인이라면 방향이 반대여야
한다 — 확대 아티팩트가 가장 심한 imgsz 1024 에서 대조군 성능비가 **가장 높고**
(82%), 아티팩트가 아예 없는 imgsz 128 에서 **가장 낮다**(50%). 오히려 82% 는
흐려진 상태로 잰 값이라 **과소평가**일 가능성이 크다.

그래도 깨끗한 실험은 아니다. 대조군 결과를 인용할 때 붙일 단서:
- **imgsz 256 이하 구간(비율 72% / 50%)은 양쪽 다 100% 축소라 리샘플링 방향이
  같다.** 이 구간의 비교가 가장 깨끗하다.
- imgsz 1024·512 의 82% / 70% 는 확대 아티팩트가 섞여 있어 그대로 읽지 말 것.
- 제대로 하려면 대조군을 원본 해상도 그대로 평가하거나, 확대되는 사진을 뺀
  부분집합으로 다시 재야 한다. 지금 데이터로는 1024 에서 축소되는 사진이 2장
  뿐이라 그 방식은 표본이 부족하다.

이 한계는 D2~D3 진행 중에는 인지하지 못했고, 나중에 "크기가 다른 사진을
리사이즈하면 노이즈가 되지 않느냐"는 질문을 받고 배율 분포를 직접 재면서
드러났다. **원본 크기 편차가 큰 데이터셋에서는 imgsz 로 맞추는 것만으로
전처리가 통일되지 않는다** — 배율 분포를 따로 확인할 것.

### 읽어낸 것 3 보강 — 대조군 격차는 클래스 구성 차이가 아니다

위 표에서 보이듯 small_control 은 단순히 "작은" 세트가 아니라 **`blur bolt` 가
몰려 있는**(전체 132건 중 62건) 세트이기도 하다. 그래서 4종 평균 mAP 비율
(93%->89%->71%->61%)에는 크기 효과와 클래스 구성 효과가 섞여 있다.

양쪽 모두 표본이 충분한 유일한 클래스인 `bolt nut`(val 99건 / control 87건)만
떼어내 다시 보면:

| val 객체 중앙값 | 67.3px | 33.6px | 16.8px | 8.4px |
|---|---|---|---|---|
| yolo11n val AP50 (nut) | 0.944 | 0.904 | 0.825 | 0.542 |
| yolo11n control AP50 (nut) | 0.771 | 0.634 | 0.591 | 0.271 |
| **비율** | **82%** | **70%** | **72%** | **50%** |
| yolo11s 비율 | 87% | 66% | 63% | 0%* |

\* yolo11s 8.4px 은 학습 실패 런(아래 참고).

클래스 구성 효과를 제거해도 **작아질수록 대조군이 뒤처지는 방향은 그대로다.**
읽어낸 것 3 의 결론은 유지된다. 다만 4종 평균으로 볼 때보다 큰 객체 구간에서도
격차가 이미 크다(93% 가 아니라 82%) — 4종 평균이 오히려 격차를 가리고 있었다.

### 사후 정정 (D3, 2026-08-01) — NPU-BOLT yolo11s 의 작은 스케일 수치는 발산한 값이었다

아래 D3 절에서 밝혔듯 `npu-bolt + yolo11s + imgsz 256/128` 런은 학습이 NaN 으로
발산했고, ultralytics 가 발산 직전 best.pt 를 남기는 바람에 "그냥 성능이 낮은
런"처럼 보였다. 따라서 **D2 표의 npu-bolt yolo11s s025(0.358)·s012(0.012)와 그
행이 들어간 대조군 비율(79%/61%/0%)은 신뢰할 수 없다.** 정정된 수치는 D3 절 참고.
D2 의 결론 자체(대조군 비율이 단조 감소한다)는 발산이 없었던 yolo11n 곡선
(93%->89%->71%->61%)과 `bolt nut` 단독 비교로 이미 성립한다.

## D3 — YOLO26(STAL) 벤치마크

### 선행 과제 — NPU-BOLT 클래스 계층화 재분할

D2 가 남긴 선행 과제(무작위 분할 탓에 test 의 희소 클래스가 2~3건뿐)를
`sod/data/npubolt.py: _stratified_split` 로 해결했다. 이미지 하나에 여러 클래스가
섞여 있어 단순 층화가 안 되므로, **희소한 클래스부터 배치**하며 각 분할의 잔여
필요량을 채우는 iterative stratification 을 쓴다 — 희소 클래스를 나중에 배치하면
이미 다른 이유로 배정된 이미지들 때문에 맞출 여지가 없어진다.

| 클래스 | 이전 test | 새 test | 새 비율(train/val/test) |
|---|---|---|---|
| blur bolt | 2 | **10** | 0.71 / 0.14 / 0.14 |
| bolt side | 3 | **8** | 0.68 / 0.16 / 0.16 |
| bolt head | 29 | 38 | 0.70 / 0.15 / 0.15 |
| bolt nut | 120 | 101 | 0.70 / 0.15 / 0.15 |

효과가 바로 나타났다. D2 옛 분할에서는 val 과 test 가 0.065 벌어져 있었는데
(0.547 vs 0.482), 새 분할에서는 0.002~0.006 이다(0.5815 vs 0.5797 등).
**희소 클래스가 test 에 몇 건밖에 없어서 생긴 잡음이었고, 분할 하나로 평가
재현성이 확보됐다.** `bolt side` 는 여전히 val/test 8건씩이라 적지만 이 데이터로
가능한 최선이다.

### 함정 — 학습이 NaN 으로 발산하는데 조용히 넘어간다

**D2 의 "미해결" 항목(yolo11s 8.4px 이 0.012 로 무너짐)은 소형 객체 효과가
아니라 학습 발산이었다.**

`results.csv` 를 열어보니 `npu-bolt + yolo11s + 작은 imgsz` 조합에서 손실이
중간에 NaN 이 된다 — s012 은 epoch 16 부터(36 epoch 중 21), s025 도 12 epoch.
나머지 22개 런은 NaN 이 0이다.

문제는 **이게 조용히 일어난다**는 것이다. ultralytics 는 발산해도 계속 돌다가
patience 로 조기 종료하고 **발산 직전의 best.pt** 를 남기므로, 결과만 보면
"그냥 성능이 낮은 런"과 구별이 안 된다. D2 에서 이 0.012 를 "작아서 어렵다"의
데이터 포인트로 읽을 뻔했다.

원인은 혼합정밀(fp16) 오버플로였다. `amp=False` 로 다시 돌리니 NaN 이 0이 되고
정상 수렴한다:

| npu-bolt yolo11s | 발산(amp=True) | 복구(amp=False) |
|---|---|---|
| s025 val / small_control | 0.3847 / 0.2367 | 0.3868 / **0.2736** |
| s012 val / small_control | 0.0083 / 0.0000 | **0.0836** / **0.0591** |

val 은 거의 같은데 small_control 이 크게 오른 데 주목할 것 — 발산 직전 가중치는
**어려운 세트에서 더 손해**를 본다. D2 가 보고한 대조군 비율 중 yolo11s 행
(79%/61%/0%)이 실제보다 낮게 나온 이유다.

**조치**: `scripts/02_train_baseline.py` 에 `nan_epochs()` 를 넣어 학습 직후
`results.csv` 를 검사하고, NaN 이 있으면 `amp=False` 로 한 번 자동 재학습한다.
그래도 NaN 이면 결과 행에 `nan_epochs > 0` 을 남겨 곡선에서 배제할 수 있게 했다.
결과 행에 `amp` 필드도 기록한다. 이 방어가 없었으면 YOLO26 도 같은 조건에서
발산해 **"YOLO26 이 소형 구간에서 나쁘다"는 잘못된 결론**이 나올 수 있었다.

### baseline 재측정 (새 분할, NaN 복구 후)

| imgsz | 1024 | 512 | 256 | 128 |
|---|---|---|---|---|
| yolo11n val mAP50 | 0.582 | 0.468 | 0.356 | 0.138 |
| yolo11n small_control | 0.443 | 0.400 | 0.213 | 0.045 |
| yolo11s val mAP50 | 0.618 | 0.490 | 0.387 | **0.084** |
| yolo11s small_control | 0.513 | 0.413 | 0.274 | 0.059 |

(s025·s012 의 yolo11s 는 `amp=False`)

### 읽어낸 것 — 용량 효과는 "소형 구간"이 아니라 "소형이면서 데이터가 충분한 구간"에서만 성립한다

D2 의 결론 2("모델 용량은 소형 구간에서만 값을 한다")를 한 단계 좁혀야 한다.
발산을 걷어내고 보면 극단적으로 작은 구간에서 부호가 뒤집힌다:

| | MVTec 14.1px | NPU-BOLT 8.4px |
|---|---|---|
| yolo11n | 0.331 | 0.138 |
| yolo11s | 0.472 (**+0.141**) | 0.084 (**-0.054**) |

MVTec(train 269장)에서는 용량이 도움이 되는데 NPU-BOLT(train 224장, 게다가
클래스 4종에 희소 클래스 포함)의 극소형 구간에서는 오히려 해롭다. 큰 모델이
amp 를 꺼야 겨우 수렴할 만큼 학습이 불안정하다는 것과 같은 방향의 증거다.
**"작을수록 큰 모델이 낫다"가 아니라 "작을수록 큰 모델이 학습 자체를 못 할
위험이 커진다"** 가 이 구간의 정확한 서술이고, D3 의 YOLO26 비교도 이 구분을
전제로 읽어야 한다.

### YOLO26 결과 — 세 데이터셋이 서로 다른 답을 낸다

`scripts/05_compare_models.py` 로 같은 데이터셋·스케일·프로토콜에서 YOLO26 -
YOLO11 을 뺀 값. 파라미터 수는 비교 가능한 급이다(yolo26n 2.57M vs yolo11n
2.59M, yolo26s 10.0M vs yolo11s 9.41M). 전체 표는 `outputs/d3_yolo26_vs_yolo11.md`,
곡선은 `outputs/d3_ap_curve.png`.

mAP@0.5:0.95(val) 기준 요약 — 스케일 4단계 x 모델 2급 = 8개 조합:

| 데이터셋 | 평균 차이 | 중앙값 | YOLO26 우세 조합 |
|---|---|---|---|
| mvtec-screws | **-0.033** | -0.015 | 1/8 |
| npu-bolt | -0.011 | -0.006 | 2/8 |
| pcbsmd | **+0.007** | +0.010 | 6/8 |

**결론: YOLO26 이 소형 객체에서 YOLO11 을 일관되게 앞선다는 증거가 없다.**
방향이 데이터셋마다 다르고, 폭도 대부분 0.01~0.03 수준이다. STAL(Small Target
Assignment)이 겨냥한 게 바로 이 구간인데, 세 데이터셋 중 한 곳(PCBsmd)에서만
평균 +0.007 로 아주 작게 앞선다.

데이터셋별로 보면:

- **MVTec 은 YOLO26 이 분명히 진다** (8개 중 7개 조합에서 열세). 특히 yolo11n
  대비 28.2px 에서 -0.089, 14.1px 에서 -0.069 다. val 647건으로 표본도
  충분하다. 세 데이터셋 중 유일하게 회전 박스를 외접 AABB 로 변환한 데이터셋
  (결정 3)이고 클래스가 13종으로 가장 많다 — 어느 쪽이 원인인지는 이 실험으로
  가려지지 않는다.
- **NPU-BOLT 는 판정 불가.** 8개 조합에서 부호가 계속 뒤집히고 폭도 0.03 이내다.
  val 161건 / 대조군 213건이라 이 정도는 표본 잡음 범위다.
- **PCBsmd 는 YOLO26 이 근소하게 앞선다** (6/8, 평균 +0.007). val 2,661건으로
  표본이 가장 크다. 다만 **mAP@0.5 로는 이 차이가 안 보인다** — 세 스케일에서
  mAP@0.5 차이가 -0.0005~+0.0001 인데 mAP@0.5:0.95 는 +0.007~+0.014 다.
  D2 에서 기본 지표를 mAP@0.5:0.95 로 바꾼 판단이 여기서 실제로 값을 했다.

한 가지 규칙성처럼 보였다가 무너진 것: "각 데이터셋이 무너지는 최극단에서
YOLO26 이 뒤집혀 진다"(MVTec 14.1px -0.069, NPU-BOLT 10.1px -0.015, PCBsmd
yolo26n 8.4px -0.015). 그런데 **PCBsmd 의 yolo26s 는 같은 8.4px 에서 +0.023 으로
반대**다. 규칙이 아니라 우연의 일치였다.

### 비교의 한계 — 하이퍼파라미터를 YOLO11 기준으로 고정했다

이 비교는 "**YOLO11 용으로 정한 학습 조건에서** YOLO26 이 더 나은가"를 잰
것이다. 두 모델은 100 epochs / patience 30(PCBsmd 는 50/15) / 동일 lr / AutoBatch
로 같게 돌렸다. YOLO26 은 NMS-free 구조 등 설계가 달라 최적 조건이 다를 수
있고, 특히 MVTec·NPU-BOLT 의 imgsz 128 런은 양쪽 다 best 가 마지막 epoch 근처라
학습이 덜 된 상태다. **"YOLO26 이 나쁜 모델"이 아니라 "이 프로토콜을 그대로
옮겨서는 이득이 없다"** 가 이 실험이 지지하는 문장이다. 모델별 튜닝까지 하는
건 D3 스코프를 넘으므로 여기서 멈추고, D4 이후는 D2 baseline(yolo11)을 계속
기준으로 쓴다.

### 함정 재확인 — NaN 발산은 모델 계열과 무관하다

`npu-bolt + s급 + imgsz 256` 조합에서 yolo26s 도 발산했다(yolo11s 와 정확히 같은
조건). 방어 로직이 자동으로 `amp=False` 재학습해 0.407 을 얻었다 — 없었으면
발산값이 그대로 "YOLO26 이 소형에서 나쁘다"의 근거로 들어갔을 것이다.
**발산은 모델 계열이 아니라 데이터셋 x 모델 크기 x 해상도 조건에서 나온다.**

### 운영 함정 — 호스트 절전으로 학습이 13시간 멈췄다

PCBsmd YOLO26 첫 런에서 호스트가 절전에 들어가며 CUDA 컨텍스트가 끊겼는데,
ultralytics 가 그 상태로 **무한 대기**에 빠졌다. 프로세스는 살아 있어 겉보기엔
정상이었고(13시간 동안 CPU 2분 32초), 로그 마지막 줄도 그대로 남아 있어
"멈춤"과 "느림"이 구분되지 않았다.

정지 감지를 붙이면서 WSL 특유의 함정을 두 개 더 밟았다:

- `nvidia-smi --query-compute-apps` 는 **WSL 에서 학습 중에도 항상 빈 결과**다
  (GPU 패스스루가 프로세스별 정보를 보고하지 않음). 이걸 "GPU 프로세스 없음 =
  정지" 신호로 쓰면 상시 참이 된다.
- `ps -o cputimes=` 가 빈 값을 반환하고 `find -newermt '-16 minutes'` 도 불안정
  했다. 둘 다 빈 값이라 정지 조건이 항상 성립해 오경보가 두 번 났다.

최종적으로 쓰는 신호는 **모든 `results.csv` 의 총 줄 수(= 완료된 epoch 수)** 다.
epoch 이 하나라도 끝나면 반드시 증가하고 우회할 여지가 없다. 간접 신호(pid,
GPU 조회, 파일 mtime) 대신 **진행 그 자체를 세는 값**을 쓸 것.

## D4 — SAHI 타일링 추론

### 무엇을 비교했나

`scripts/06_sahi_eval.py`. 재학습 없이 D2/D3 의 `best.pt` 를 그대로 쓰고,
같은 가중치로 **full-image 추론**과 **타일링 추론**을 둘 다 돌려 뺀다.
타일 크기는 학습 imgsz 와 같게 잡아, 타일이 리사이즈 없이 그대로 모델에 들어간다.

평가는 ultralytics 가 아니라 COCOeval 로 새로 짰다(`sod/eval/coco.py`) —
D4 의 질문에 면적 구간별 AP 가 직접적인 답이기 때문이다. 평가 구현이 다르면
수치가 D2/D3 표와 소수점까지 같지 않으므로, **비교 대상인 full-image 수치도 이
경로로 다시 측정**했다. 표의 delta 는 순수하게 "타일링을 켰는가"의 차이다.

+0.013)뿐이다. 계획서 3장이 인용한 "재학습 없이 소형 객체 AP +6~14%p"
(Akyon et al., 2022)는 이 설정에서 재현되지 않는다.

### 왜 이렇게 되는가 — 손해가 축소 배율을 그대로 따라간다

원인은 **학습 때 본 객체 크기와 타일 안에서 보이는 객체 크기의 불일치**다.
full-image 경로는 원본을 `imgsz` 로 줄여서 보는데, 타일링 경로는 타일을 원본
해상도 그대로 본다. 그래서 불일치 배율은 정확히 **`max(원본 변) / imgsz`**,
즉 full-image 경로가 원본을 줄이는 배율과 같다.

| 축소배율 | 1.25 | 1.88 | 2.5 | 3.75 | 5 | 7.5 | 10 | 15 |
|---|---|---|---|---|---|---|---|---|
| d(mAP50-95) 범위 | -0.004~-0.005 | -0.049~-0.080 | -0.023~-0.046 | -0.065~-0.143 | -0.017~-0.053 | -0.100~-0.250 | -0.043~-0.128 | -0.123~-0.139 |

배율이 커질수록 손해가 커진다. 유일하게 손익분기에 닿은 건 배율 1.25 인
PCBsmd imgsz 1024(-0.004)이고, 유일한 개선은 이미지 크기 편차가 커서 상당수
이미지가 애초에 imgsz 보다 작은 NPU-BOLT imgsz 1024 다 — **그 이미지들에서는
타일링을 해도 사실상 원본 그대로라 불일치가 없다.**

탐지 수 폭증(최대 407배)과 속도 저하(최대 97배)도 같은 원인이다. 모델이
학습 때보다 몇 배 큰 객체를 보면 한 객체 위에 조각난 오탐을 여러 개 만든다.

### 결론 — SAHI 는 "재학습 없이 얹는" 기법이 아니다, 적어도 이 방법론에서는

SAHI 의 전제는 **탐지기가 타일 해상도에서 학습돼 있다**는 것이다. 이 프로젝트의
D2 방법론은 반대로 **원본을 줄여서** 학습하므로, 두 전제가 정면으로 충돌한다.
계획서 3장이 SAHI 를 "가장 싸게 시도해볼 수 있는 개선"으로 넣은 근거(재학습
불필요)는 **우리 설정에서는 성립하지 않는다** — 공짜가 아니라 부호가 뒤집힌다.

이건 SAHI 논문 결과에 대한 반증이 아니다. 원 논문은 원본 해상도로 학습한
탐지기에 타일링을 얹었고, 우리는 축소 학습한 탐지기에 얹었다. **같은 기법을
다른 전제 위에 올리면 부호가 바뀐다는 실측**이다.

D5 이후로 넘기는 후속 항목: SAHI 를 제대로 평가하려면 **타일로 학습**해야 한다
(원본에서 imgsz 크기 타일을 잘라 학습셋을 만들고, 같은 방식으로 추론). 그건
추론 쪽 기법이 아니라 학습 파이프라인 변경이라 "재학습 없이"라는 D4 의 전제를
벗어나므로 별도 축으로 기록만 해둔다.

## D5 — copy-paste 증강

### 구현과 그 한계

`sod/augment/copypaste.py` + `scripts/07_build_copypaste.py`. train 분할에서만
객체를 크롭해 은행을 만들고, 기존 정답과 겹치지 않는 자리에 스케일 0.2~0.7,
90도 배수 회전으로 이미지당 5~20개를 붙인다. **val/test/small_control 은 원본
그대로 복사**한다 — 평가 세트를 건드리면 증강 전후 비교가 성립하지 않는다.

| 데이터셋 | train 이미지 | train 인스턴스 | 객체 한 변 중앙값 |
|---|---|---|---|
| npu-bolt | 224 -> 672 | 744 -> 7,621 | 151.9px -> 68.9px |
| mvtec-screws | 269 -> 807 | 3,119 -> 15,714 | - |

**마스크가 없어 bbox 직사각형 그대로 붙인다.** 세 데이터셋 어디에도 인스턴스
분할 마스크가 없고(D1) 새 라벨링은 스코프 밖이라, 원 논문(Kisantal et al.)처럼
객체만 오려낼 수 없다. 붙인 자리에 배경이 딸려온 사각형이 남는다
(`outputs/d5_copypaste_sample.jpg` 에서 육안으로 확인됨 — 어두운 크롭은 볼트로
보이지도 않는다). 알파 페더링으로 완화했을 뿐이다.

### 결과 — 개선이 baseline 이 무너지는 지점에 집중된다

val mAP@0.5:0.95 차이(증강 - baseline):

| 데이터셋 | model | 1024 | 512 | 256 | 128 |
|---|---|---|---|---|---|
| mvtec | yolo11n | -0.002 | +0.013 | +0.046 | **+0.131** |
| mvtec | yolo11s | +0.000 | +0.005 | +0.007 | **+0.229** |
| npu-bolt | yolo11n | -0.009 | -0.000 | +0.000 | **+0.014** |
| npu-bolt | yolo11s | -0.042 | +0.028 | +0.001 | **+0.107** |

**네 조합 전부 가장 작은 스케일(imgsz 128)에서 개선된다.** 그 위 구간은 대체로
0 근처다. mAP@0.5 로 보면 MVTec imgsz 128 이 +0.190(n)/+0.299(s)로 더 극적이다.

이건 copy-paste 가 하려는 일과 정확히 일치한다 — 학습셋에서 **작은 객체의
인스턴스 수 자체를 늘리는** 기법이라, 큰 객체 구간처럼 이미 인스턴스가 충분하고
성능이 포화된 곳에서는 얻을 게 없고, baseline 이 데이터 부족으로 무너지는
지점에서만 값을 한다.

### 그런데 자연 소형 대조군에서는 효과가 확인되지 않는다

계획서 3.1절이 정한 판단 기준은 곡선 자체의 개선이 아니라 **"다운스케일 곡선과
NPU-BOLT 자연 소형 대조군 사이 격차가 줄어드는가"** 였다. 그 기준으로는:

| model | imgsz | 대조군 mAP50-95 | 차이 | ctrl/val 비율 |
|---|---|---|---|---|
| yolo11n | 1024 | 0.260 -> 0.301 | +0.041 | 64% -> 76% |
| yolo11n | 512 | 0.223 -> 0.226 | +0.002 | 76% -> 76% |
| yolo11n | 256 | 0.094 -> 0.085 | -0.009 | 44% -> 40% |
| yolo11n | 128 | 0.017 -> 0.022 | +0.006 | 29% -> 31% |
| yolo11s | 1024 | 0.305 -> 0.301 | -0.004 | 65% -> 70% |
| yolo11s | 512 | 0.226 -> 0.212 | -0.014 | 66% -> 57% |
| yolo11s | 256 | 0.129 -> 0.103 | -0.026 | 53% -> 42% |
| yolo11s | 128 | 0.029 -> 0.037 | +0.007 | 74% -> 25% |

**개선 4/8 — 동전 던지기다.** 비율도 오르내려 방향이 없다. 즉 copy-paste 는
**다운스케일 곡선은 (붕괴 지점에서) 올리지만, 그 곡선이 진짜 소형 객체를
과대평가하는 정도는 못 줄인다.** D2 가 제기한 핵심 격차는 그대로 남는다.

원인 후보 순서대로: (1) 붙인 객체는 원본에서 잘라 **축소**한 것이라 실제 멀리서
찍힌 객체의 저수준 통계(센서 노이즈·모션 블러)를 갖지 않는다 — 축소가 만드는
"너무 깨끗한 작은 객체"라는 D2 2.2절의 문제를 증강도 똑같이 반복한다.
(2) 마스크 없는 사각형 아티팩트. (3) 대조군 213건이라 잡음이 크다.

**(1)이 맞다면 이건 구현 품질 문제가 아니라 방법론의 한계다** — 가진 데이터에서
잘라 붙이는 한, 원본에 없는 "멀리서 찍힌 픽셀 통계"는 만들어낼 수 없다.

### 정정 기록

첫 런(yolo11n imgsz 1024)에서 대조군이 +0.060 올라 "정확히 의도한 방향"이라고
적었고, yolo11s 세 런을 보고 "일관된다"고 적었다. 8개를 다 놓고 보니 n 과 s 가
서로 반대이고 모델 크기만 바꿔 부호가 뒤집힌다. **부분 결과로 방향을 선언하지
말 것** — 이 실험에서 안정적인 건 "가장 작은 스케일에서 val 이 개선된다" 하나뿐이다.

### 발산 재확인

`npu-bolt + s급 + imgsz 128` 에서 또 NaN 발산했다(D3 와 같은 조건, 증강
데이터셋에서도). 방어 로직이 `amp=False` 로 복구했다. 다만 이 조합의 baseline
(0.0836)도 발산 복구 런이라 같은 조건 yolo11n(0.1376)보다 낮은 이상값이었다 —
**yolo11s imgsz 128 의 +0.203(mAP50)은 증강 효과라기보다 병적인 baseline 과의
비교**라 그대로 읽으면 안 된다.

## D6 — ONNX 변환 · INT8 양자화

### 설계 — 계획서와 다르게 스케일 4단계를 전부 쟀다

계획서 3.2절은 "D2~D5 에서 가장 좋았던 조합"을 ONNX/INT8 로 변환해 재라고 했다.
대신 **스케일 4단계 전부**를 쟀다 — 스케일이 곧 객체 픽셀 크기이므로(D2),
"양자화 손실이 작은 객체에서 더 큰가"라는 이 프로젝트 고유의 질문에 답할 수
있기 때문이다. 조합 하나만 쟀으면 아래 결과는 못 봤다.

세 변형: PyTorch FP32(GPU) / ONNX FP32(CPU) / OpenVINO INT8(CPU, PTQ).
INT8 을 CPU 로 재는 이유는 인용한 선행 사례(Raspberry Pi 5, YOLO11n FP32->INT8
12.7->16.1 FPS)가 엣지 CPU 기준이고 INT8 가속이 의미 있는 것도 그쪽이라서다.
RTX 4070 에서는 FP16 이 이미 빨라 INT8 이득이 안 보인다.
**속도는 같은 기계 안에서 상대 비교로만 읽을 것** — WSL 위 CPU FPS 는 절대값으로
다른 논문과 비교할 수 없다.

### 결과 (yolo11s, val 기준)

| 데이터셋 | imgsz | FP32(CPU) | INT8 | 절대 | 상대 | 크기 | 지연시간 | 배속 |
|---|---|---|---|---|---|---|---|---|
| mvtec | 1024 | 0.9232 | 0.9201 | -0.0031 | -0.3% | 38.0->10.2MB | 95.2->54.6ms | 1.74x |
| mvtec | 512 | 0.9077 | 0.9069 | -0.0008 | -0.1% | 37.8->10.2MB | 25.2->14.9ms | 1.69x |
| mvtec | 256 | 0.8610 | 0.8571 | -0.0039 | -0.5% | 37.8->10.2MB | 8.08->5.54ms | 1.46x |
| mvtec | 128 | 0.2960 | 0.2783 | **-0.0177** | -6.0% | 37.8->10.2MB | 3.87->3.23ms | 1.20x |
| npu-bolt | 1024 | 0.4592 | 0.4202 | **-0.0390** | -8.5% | 38.0->10.2MB | 97.1->52.9ms | 1.83x |
| npu-bolt | 512 | 0.3450 | 0.3351 | -0.0099 | -2.9% | 37.8->10.2MB | 24.6->14.9ms | 1.65x |
| npu-bolt | 256 | 0.2433 | 0.2367 | -0.0066 | -2.7% | 37.8->10.2MB | 8.16->5.31ms | 1.54x |
| npu-bolt | 128 | 0.0433 | 0.0449 | +0.0016 | +3.7% | 37.8->10.2MB | 3.82->3.00ms | 1.27x |

### 확실한 것 — 크기와 속도

- **크기는 항상 3.7배 줄어든다**(37.8 -> 10.2MB). imgsz·데이터셋과 무관하다.
  ONNX FP32 파일 크기가 imgsz 와 거의 무관한 것도 확인된다(가중치가 대부분이라).
- **속도 이득은 입력이 클수록 크다**: imgsz 1024 에서 1.74~1.83배, 128 에서
  1.20~1.27배. 두 데이터셋에서 같은 추세다. 작은 입력은 연산량 자체가 적어
  INT8 가속이 먹을 여지가 작다. 인용한 선행 사례의 1.27배(12.7->16.1 FPS)와
  같은 자릿수다.

### 확실하지 않은 것 — "양자화가 작은 객체를 더 해치는가"에는 답 못 한다

MVTec 만 보면 상대 손실이 0.1~0.5% 로 평탄하다가 마지막 스케일에서 6.0% 로
튀어, "작은 객체에서 양자화 손실이 커진다"로 읽힌다. **그런데 NPU-BOLT 는 정확히
반대로 8.5% -> 2.9% -> 2.7% -> +3.7% 다.** 두 데이터셋의 추세가 어긋나므로
객체 크기로 설명되지 않는다.

더 그럴듯한 설명은 **FP32 성능이 낮은 지점일수록 상대 손실이 요동친다**는 것이다.
상대 손실이 큰 두 칸은 MVTec imgsz 128(FP32 0.296)과 NPU-BOLT imgsz 1024
(FP32 0.459)인데, 후자는 큰 객체 쪽이다. 절대 손실로 보면 전부 0.04 이내이고,
mAP 가 낮은 구간에서는 같은 절대 손실이 큰 상대 손실로 보인다. NPU-BOLT
imgsz 128 의 +3.7% 도 FP32 가 0.0433 이라 잡음이 그대로 비율에 증폭된 것이다.

**정정 기록**: MVTec 4회만 나온 시점에 "양자화 손실은 작은 객체에서 불균형하게
크다"고 단정했는데, NPU-BOLT 에서 뒤집혔다. D5 에서와 같은 실수다 —
**한 데이터셋 결과로 방향을 선언하지 말 것.**

### ONNX 변환 자체는 거의 무손실

PyTorch(GPU) -> ONNX(CPU) 차이는 8개 중 7개가 ±0.004 이내다. 예외는 MVTec
imgsz 128(-0.0196)인데, 이 구간은 mAP 자체가 0.3 언저리라 실행 환경 차이가
비율로 증폭되는 지점이다. **정확도 손실의 실질적 원인은 변환이 아니라 INT8
양자화**로 봐도 된다.

### 실무적 결론

INT8 양자화는 **크기 3.7배, 속도 1.2~1.8배를 정확도 0.04 이내(대개 0.01 이내)
손실로 산다.** 이 프로젝트의 대상(작고 얇은 부품)에서도 그 거래는 유리하다.
다만 **소형 구간에서는 속도 이득이 1.2배까지 줄어들므로**, 엣지 배포에서
"작은 입력 + INT8" 조합은 기대만큼 빨라지지 않는다는 점은 감안해야 한다.

## D7 — Weighted Boxes Fusion (모델 앙상블)

### 설계

`scripts/09_wbf_ensemble.py`. 데이터셋·스케일마다 이미 학습된 네 모델
(yolo11n/s, yolo26n/s)의 예측을 모아 세 가지를 비교한다: 최고 단일 모델 /
NMS 앙상블(겹치는 박스를 **버림**) / WBF(겹치는 박스를 **합쳐 새 박스를 만듦**).

**NMS 를 같이 재는 게 핵심이다.** 그래야 "앙상블이 좋은 것"과 "합치는 게 버리는
것보다 나은 것"을 분리할 수 있다. 계획서 3.3절도 두 비교를 다 요구한다.
평가는 D4 와 같은 COCOeval 경로이고 구성원 단독 성적도 같은 경로로 다시 재므로,
표 안의 비교는 평가 구현 차이에 오염되지 않는다.

### 결과 — WBF > NMS 는 맞지만, 소형 구간에서 둘 다 뒤집힌다

mAP@0.5:0.95(val) 기준, 최고 단일 모델 대비:

| 스케일 | mvtec | npu-bolt | pcbsmd | 평균 |
|---|---|---|---|---|
| 1.0 | +0.0092 | +0.0151 | +0.0127 | **+0.0123** |
| 0.5 | +0.0061 | +0.0062 | +0.0055 | **+0.0059** |
| 0.25 | +0.0012 | +0.0240 | +0.0052 | **+0.0101** |
| 0.125 | -0.0197 | -0.0484 | -0.0132 | **-0.0271** |

- **WBF 가 최고 단일을 이긴 건 12개 중 9개**, 진 3개는 전부 **가장 작은 스케일**이다.
  세 데이터셋에서 예외 없이 같은 지점에서 뒤집힌다.
- **NMS 앙상블은 12개 중 4개만 최고 단일을 이긴다.** 즉 "여러 모델을 합치면
  좋아진다"가 아니라 **"어떻게 합치느냐가 좌우한다"** 가 맞는 서술이다. NMS 는
  성능이 낮은 구성원(예: mvtec imgsz 256 의 yolo26n, mAP50-95 0.706 vs 최고 0.858)의
  박스가 좋은 박스를 밀어내 손해를 본다.

### 왜 소형 구간에서 WBF 가 지는가

WBF 는 겹치는 박스들의 **좌표를 신뢰도 가중 평균**한다. 이는 구성원들이 비슷하게
잘 위치를 잡는다는 전제 위에 있다. 가장 작은 스케일에서는 구성원들의 위치
추정이 제각각이라(D2 에서 확인한 대로 이 구간은 mAP@0.5:0.95 가 특히 무너진다 —
"찾았는가"보다 "얼마나 정확히 감쌌는가"가 먼저 무너진다) 평균이 오히려 어느
구성원보다도 나쁜 박스를 만든다. 하나만 고르는 NMS 가 이 구간에서 상대적으로
덜 손해 보는 것도 같은 이유다(mvtec imgsz 128 에서 NMS 만 유일하게 +0.0096).

**D2 의 "작아질 때 먼저 무너지는 건 위치 정확도"라는 발견이 앙상블 층에서 그대로
반복된다.** 소형 객체에서는 좌표를 평균하는 모든 후처리가 같은 위험을 안는다.

### 비용

앙상블은 구성원 넷을 전부 돌려야 하므로 **추론 비용이 4배**다(표의 추론합:
mvtec 약 20초, pcbsmd 약 43초 for val 전체). 병합 자체는 1초 미만이라 무시할
수준이다. 얻는 게 평균 +0.006~+0.012 이므로, **정확도 한 자리를 더 짜내야 하는
상황이 아니면 비용 대비 이득이 크지 않다.** D6 이 INT8 로 속도를 1.2~1.8배
벌어온 것과 정반대 방향의 거래다.

## D8 — 능동 학습 시뮬레이션

### 설계

`scripts/10_active_learning.py`. MVTec(train 269장), imgsz 512, yolo11n.
전체의 10%(26장)로 시작해 라운드마다 10%씩 라벨을 "공개"하며 5라운드. 두 전략을
**동일한 초기 세트**에서 출발시킨다 — 시작점이 다르면 이후 차이가 전략 때문인지
출발점 때문인지 못 가른다. 시드 2개.

불확실성 점수는 단순화했다: 탐지가 없으면 1.0, 있으면 `1 - 평균 신뢰도`.
PPAL 의 난이도 보정·다양성 샘플링은 뺐다 — 재려는 건 "불확실성 기반 선택이
무작위보다 나은가" 하나이고, 구성 요소를 늘리면 무엇이 효과를 냈는지 못 가른다.

### 결과 1 — 라벨 20~30%면 전체 성능의 90~98%에 닿는다

| 라벨 비율 | 26(10%) | 52(19%) | 78(29%) | 104(39%) | 130(48%) | 156(58%) |
|---|---|---|---|---|---|---|
| 무작위 평균 mAP50 | 0.281 | 0.895 | 0.975 | 0.985 | 0.986 | 0.986 |
| 전체 데이터(0.9894) 대비 | 28% | **90%** | **98.5%** | 99.6% | 99.6% | 99.7% |

곡선이 19~29% 구간에서 사실상 포화된다. **이 데이터셋에서 라벨링 예산의 70%는
성능에 기여하지 않는다** — "작은 객체는 이미지당 인스턴스가 많아 라벨링 비용이
크다"는 문제에 대한 실용적인 답이 된다. 다만 MVTec 은 통제된 촬영에 배경이
일정해 포화가 특히 빠를 수 있다(D2 에서 확인한 데이터셋별 난이도 차이).

### 결과 2 — 불확실성 샘플링이 무작위보다 낫다는 증거는 없다

라운드별 (불확실성 - 무작위) mAP50, 두 시드 평균: -0.032 / +0.003 / -0.010 /
+0.001 / +0.002 / +0.003. **평균 -0.005, 부호가 계속 뒤집힌다.**

### 왜 안 되는가 — 초반에는 무작위로 퇴화한다

원인이 선택 결과에 그대로 남아 있다. 두 전략이 고른 이미지의 겹침 비율:

| 라운드 | r0 | r1 | r2 | r3 | r4 | r5 |
|---|---|---|---|---|---|---|
| 겹침 | 100%(동일 출발) | **96~100%** | 68% | 62% | 64% | 70% |

**r1 에서 시드 1 은 52장을 100% 똑같이 골랐다.** 초기 모델이 대부분 이미지에서
아무것도 탐지 못 하면 불확실성 점수가 전부 1.0 이 되고, 정렬이 안정적이라 원래
순서(= 무작위로 섞인 pool)가 그대로 유지되기 때문이다. r2 부터 겹침이 62~70%로
떨어져 비로소 다른 선택을 하지만, **그때는 이미 곡선이 포화**라 뭘 골라도
차이가 없다.

정리하면 **불확실성 샘플링은 이미 어느 정도 작동하는 모델을 전제하는데, 라벨
효율이 가장 중요한 건 그 모델이 없는 초반(cold start)이다.** 이 구간에서 쓰려면
불확실성 말고 다른 신호(다양성·대표성)가 필요하다 — PPAL 이 다양성 샘플링을
같이 쓰는 이유가 여기 있을 것이다. 그 조합까지 재는 건 이번 스코프 밖이다.

### 측정된 잡음 — 같은 데이터로도 0.063 벌어질 수 있다

seed0 r0 은 두 전략이 **완전히 같은 26장**을 썼는데 mAP50 이 0.3446 vs 0.2817 로
갈렸다. 반면 seed1 r0 은 0.2167 로 정확히 재현됐다. `batch=-1`(AutoBatch)이 그
시점 VRAM 여유에 따라 다른 배치 크기를 고르는 게 원인으로 보인다.

**비결정성이 간헐적이라 잡음 바닥을 단일 값으로 못 말한다.** 다만 관측된 최대
0.063 은 위 전략 차이(-0.032~+0.003)와 같은 자릿수이므로, **이 실험의 해상도로는
전략 차이를 판정할 수 없다**는 게 정직한 결론이다. 재현성이 필요한 실험에서는
`batch` 를 고정할 것.

### 초기 세트 선택이 전략 선택보다 영향이 크다

10% 시점 성능이 시드에 따라 0.217~0.345 로 벌어진다. 어느 26장으로 시작하느냐가
어떤 전략을 쓰느냐보다 훨씬 크게 작용하고, 29% 시점에는 그 차이가 거의 사라진다
(0.973 vs 0.977). 라벨링 예산을 짤 때 **알고리즘보다 초기 표본을 어떻게 잡느냐가
먼저**라는 실무적 함의가 있다.

## D9 — Grad-CAM / Eigen-CAM 설명 가능성

### 설계 — 그림이 아니라 지표로

계획서 3.5절은 "왜 작은 객체를 놓치는지 시각적 근거"를 요구한다. 히트맵 그림만
내면 "작을수록 어렵다"의 재확인에 그치므로 지표로 만들었다:

    concentration = (정답 박스 안 CAM 평균) / (이미지 전체 CAM 평균)

`scripts/11_cam_diagnose.py`, 세 데이터셋 x 2모델 x 4스케일 = 24조합.
CAM 은 Detect 헤드가 받는 **가장 고해상도 특징맵(P3, stride 8)** 에서 뽑는다.

### 착수하며 밟은 함정 다섯 개

1. **CAM 해상도.** 처음엔 Detect 직전 모듈(P5, stride 32)을 썼는데 imgsz 256 에서
   CAM 이 8x8 밖에 안 나와 정답 박스가 격자에 뭉개졌다(GT 면적이 48%로 부풀었다).
   P3 로 바꿔 32x32 를 얻었다.
2. **Eigen-CAM 부호 뒤집힘.** SVD 는 특이벡터 부호를 임의로 정한다. `cam.mean()<0`
   이면 뒤집는 보정을 넣었는데 **작동하지 않았다** — 평균을 뺀 행렬의 첫 특이벡터는
   평균이 0 근처라 그 검사가 동전 던지기였고, 실측 8장 중 5장이 반전된 채 통과해
   concentration 0.79~0.94(= "배경에 더 반응")로 나왔다. 활성 에너지(채널 L2 노름)
   와의 상관으로 부호를 정하도록 고쳤다.
3. **ultralytics 가 기울기를 차단한다.** 추론용으로 로드하면 파라미터 256개가 전부
   `requires_grad=False` 라 backward 가 "element 0 of tensors does not require grad"
   로 죽는다.
4. **집계 중 None.** Grad-CAM 의 ReLU 로 CAM 이 전부 0 이면 concentration 이 None 이라
   평균 계산에서 죽는다.
5. **결과 파일 동시 쓰기.** 패치 전 프로세스와 패치 후 프로세스가 같은 jsonl 에
   append 해 같은 조합에 다른 값이 찍혔다. 전부 죽이고 단일 프로세스로 재생성한 뒤,
   같은 조합을 두 번 돌려 **완전히 동일**함을 확인하고서야 결과로 받아들였다.

### 결과 — 이 지표는 성능을 설명하지 못한다

24조합에서 CAM 지표와 mAP@0.5:0.95 의 상관:

| 지표 | mAP50-95 와의 상관 |
|---|---|
| Grad-CAM concentration | **-0.08** |
| Grad-CAM 안/밖 비율 | **+0.03** |
| Eigen-CAM concentration | -0.24 |
| (참고) GT 면적 비율 vs Grad-CAM concentration | **-0.65** |

**셋 다 성능과 무관하다.** 반면 concentration 은 정답 박스 면적 비율과 -0.65 로
강하게 얽혀 있다 — NPU-BOLT·PCBsmd 처럼 박스가 이미지의 2~8% 뿐인 데이터셋에서는
전체 평균이 사실상 배경값이라 비율이 자동으로 커진다(15~32). MVTec 은 박스가
24~36% 라 2~5 에 머문다. **이 지표는 "모델이 객체를 잘 본다"가 아니라 "정답 박스가
작다"를 재고 있었다.**

반례도 명확하다: mvtec yolo11s imgsz 512 는 concentration 1.00(= 객체와 배경을 전혀
구분 안 함)인데 mAP@0.5:0.95 는 0.9045 로 최상위권이다.

### 그래서 D9 의 결론

**CAM 기반 집중도 지표로는 "왜 작은 객체를 놓치는가"에 답할 수 없다.**
계획서 3.5절이 기대한 "활성이 약한가 vs 엉뚱한 배경에 반응하는가"의 판별은
이 도구로는 안 된다 — 지표가 면적에 지배되고 성능과 상관이 없기 때문이다.

설명 가능성 도구는 **정성적 확인용으로만** 쓴다(`outputs/d9_grad_*.jpg`,
`outputs/d9_eigen_*.jpg`). 정량 진단이 필요하면 CAM 이 아니라 **오류 유형 분해**
(놓침/오탐/위치오차/클래스오류)로 가야 한다 — D2 가 "작아질 때 먼저 무너지는 건
위치 정확도"를 mAP@0.5 와 mAP@0.5:0.95 의 격차로 잡아낸 것이 그 방향의 예다.

이건 D4(SAHI)와 같은 성격의 결과다. 문헌에서 잘 쓰이는 도구라도 **전제가 다른
설정에 그대로 올리면 답을 못 준다.**

### 부수적으로 확인된 것 — Eigen-CAM 은 고해상도에서 객체를 못 짚는다

부호를 고친 뒤에도 imgsz 1024/512 에서 concentration 이 0.88~1.16 으로 1.0 근처다
(두 모델 x 세 데이터셋에서 재현). 128x128 특징맵에서는 배경 텍스처가 분산을
지배해 첫 주성분이 객체와 정렬되지 않는다. **Eigen-CAM 의 "첫 주성분 = 객체"는
가정이지 보장이 아니다.** Grad-CAM 은 기울기가 방향을 알려주므로 이 문제가 없다
(다만 위에서 보듯 성능 설명력은 별개다).
